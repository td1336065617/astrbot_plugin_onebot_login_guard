# OneBot 登录守护（astrbot_plugin_onebot_login_guard）需求分析

> 版本：v1.0（草稿）　|　目标环境：AstrBot >= 4.13、OneBot v11（NapCat / Lagrange / go-cqhttp）
> 状态：待评审

---

## 1. 背景与问题

AstrBot 接入 QQ 非官方机器人时，走的是 OneBot v11 反向 WebSocket（aiocqhttp 适配器），协议端通常是 **NapCat / Lagrange / go-cqhttp**。

这类方案有一个共同痛点：**登录态会掉**。

- QQ 侧会让会话失效（实测 NapCat 日志：`[Login] Login Error, ErrType: 1 ErrCode: 3`）；
- 协议端随后生成登录二维码，等待人工用手机 QQ 扫描；
- **但没有人知道**——机器人静默离线，可能持续几小时甚至几天；
- 管理员往往要等到"群里怎么不回复了"才发现。

现状（实测服务器）：掉登录后

- NapCat 不再向 AstrBot 建立反向 WS，AstrBot 侧表现为"平台没连上"；
- NapCat 日志里有 `Login Error` / `二维码已保存到 .../cache/qrcode.png` / `二维码解码URL: https://txz.qq.com/p?k=...`；
- AstrBot 本身**没有任何掉线/掉登录通知机制**。

结论：缺一个「发现掉登录 → 立刻把二维码送到管理员手里」的守护插件。

---

## 2. 目标与非目标

### 2.1 目标

| 编号 | 目标 |
| --- | --- |
| G1 | OneBot 账号**掉登录**后，在可配置时限内通知管理员，并携带**二维码**（图片或可扫描链接） |
| G2 | OneBot 账号**掉线/进程不在**时，也能通知（此时可能没有二维码） |
| G3 | **恢复登录**后通知，形成闭环 |
| G4 | 通知渠道与被守护的 QQ **解耦**（QQ 挂了也能发出去） |
| G5 | 零侵入：不改 NapCat、不改 AstrBot 核心；开箱即用 |
| G6 | 可观测：WebUI 状态页 + 指令 + 结构化日志 |

### 2.2 非目标

- **不实现自动扫码登录**（QQ 安全设计，任何客户端都必须人工验证，无法绕过）。
- 不接管/修改 NapCat 的登录流程。
- 不做 QQ 风控对抗、不做协议端进程守护（进程级由 systemd 等负责）。
- 不替代 NapCat WebUI。

---

## 3. 用户与使用场景

**目标用户**：自部署 AstrBot + NapCat/Lagrange 的个人或小团队，机器人有实际群业务（审核、推送、问答）。

| 场景 | 描述 | 期望 |
| --- | --- | --- |
| S1 掉登录 | QQ 会话失效，协议端弹二维码 | 尽快收到二维码，扫码恢复 |
| S2 协议端掉线 | NapCat 进程崩溃/被杀/网络断 | 收到告警（无二维码），提示去查进程 |
| S3 二维码刷新 | 二维码过期，协议端生成新的 | 收到新二维码（不轰炸） |
| S4 恢复 | 扫码成功 | 收到"已恢复" |
| S5 日常查看 | 想确认当前是否在线 | 指令/WebUI 一看便知 |

## 4. 功能需求

### FR1 登录态探测
- **FR1.1 AstrBot 原生探测**：检查 aiocqhttp 平台实例的反向 WS 客户端数量与平台状态；无连接 → 判定"未连接"。
- **FR1.2 日志文件探测**：tail 协议端日志（记录读取偏移），按可配置正则识别：
  - 需要登录（`Login Error` / `请扫描` / `二维码`）；
  - 登录成功；
  - 二维码解码 URL。
- **FR1.3 二维码文件探测**：读取协议端二维码图片路径（默认 NapCat 的 `cache/qrcode.png`），用 mtime 判断是否刷新。
- **FR1.4 HTTP 探测（可选）**：调用 NapCat WebUI API 获取登录状态/二维码。
- **FR1.5 多实例**：一个插件实例可守护多个 OneBot 平台实例，各自配置探测源。

### FR2 二维码获取与投递
- **FR2.1** 从配置路径读取 PNG（默认 NapCat 常见路径）。
- **FR2.2** 从日志提取"二维码解码 URL"作为纯文本备选。
- **FR2.3** 图片以本地文件形式随通知发送；渠道不支持图片时自动降级为 URL。

### FR3 通知渠道
- **FR3.1 AstrBot 会话通知**：把二维码/告警发到配置的 unified_msg_origin 列表（可发到**另一个**平台，如 QQ 官方号/Telegram/企微）。
- **FR3.2 外部 Webhook**：企业微信群机器人、钉钉机器人、飞书自定义机器人、Telegram Bot API、通用 JSON Webhook。
- **FR3.3** 多渠道路由：同一事件可并发发往多个渠道，失败重试并记录。
- **FR3.4 邮件通知**：通过 SMTP 发送告警邮件（支持 SSL / STARTTLS、多收件人），二维码以附件形式携带。
- **FR3.5 多协议端多账号**：一个 AstrBot 可守护多个 OneBot 实例，各自配置探测源、状态与冷却。

### FR4 去重、节流与状态机
- **FR4.1** 同一事件（同实例 + 同类型）在冷却窗口内只通知一次（默认 10 分钟）。
- **FR4.2** 二维码**内容/mtime 变化**时重新通知（可单独开关）。
- **FR4.3** 状态恢复时发"已恢复"。
- **FR4.4** 探测源不可用时判定为 UNKNOWN，**不误报**。

### FR5 管理能力
- **FR5.1 指令**：`登录守护状态`（只读）、`登录守护二维码`（重发）、`登录守护测试`（测试通知）。
- **FR5.2 WebUI 页面**：各实例实时状态、二维码预览、最近事件、立即探测/重发/测试按钮。
- **FR5.3 事件历史**：落盘最近 N 条事件（谁、何时、什么状态、通知结果）。

### FR6 配置
- **FR6.1** 全部开关/路径/渠道/冷却通过 `_conf_schema.json` 暴露，WebUI 可视化编辑。
- **FR6.2** 敏感字段（Webhook token/secret）不写入日志、不返回给前端。

---

## 5. 非功能需求

| 编号 | 需求 |
| --- | --- |
| NFR1 可靠性 | 探测/通知异常一律自吞并记录，绝不影响 AstrBot 主流程 |
| NFR2 性能 | 默认 30~60s 轮询一次；文件读取走线程/异步，不阻塞事件循环 |
| NFR3 安全 | 不打印密钥；二维码仅发给配置的接收方；文件路径限定为配置项 |
| NFR4 兼容 | AstrBot >= 4.13、Python >= 3.10；不引入 `requests`（用 aiohttp/httpx） |
| NFR5 可移植 | 适配 NapCat/Lagrange/go-cqhttp；日志正则可覆盖 |
| NFR6 可维护 | 模块化、类型标注、ruff 通过、单测覆盖核心逻辑 |
| NFR7 规范 | 数据写 `data/`（`StarTools.get_data_dir()`），不写插件目录 |

---

## 6. 约束与依赖

- 依赖 AstrBot 插件 API：`Star` / `filter` / `context` / `register_web_api`。
- 依赖 OneBot v11 反向 WS（aiocqhttp 适配器）。
- 可选依赖 `aiohttp`（Webhook 推送）。
- 文件探测要求**插件与协议端在同一主机**（或能读到同一路径）；否则自动降级。

---

## 7. 风险与对策

| 风险 | 对策 |
| --- | --- |
| R1 协议端日志格式随版本变化 | 正则可配置 + 内置多套模板（NapCat/Lagrange/go-cqhttp） |
| R2 插件与协议端不在同一主机 | 回退到 AstrBot 原生探测（只能判"未连接"，拿不到二维码），文档明确说明 |
| R3 通知渠道也依赖 AstrBot，AstrBot 挂了发不出 | 推荐同时配置外部 Webhook（Telegram/企微），实现"跨 AstrBot"通知 |
| R4 二维码有效期短 | 高优先级事件、即时发送；二维码刷新即重发 |
| R5 误报（把正常抖动判成掉线） | 连续 N 次探测失败才判定；引入 UNKNOWN 状态 |
| R6 通知轰炸 | 冷却窗口 + 幂等键 |

---

## 8. 验收标准

| 编号 | 验收 |
| --- | --- |
| AC1 | 让协议端登出后，≤ 2 个轮询周期内收到带二维码的通知 |
| AC2 | 扫码恢复后收到"已恢复"通知 |
| AC3 | 冷却窗口内不重复轰炸；二维码刷新会重发 |
| AC4 | 协议端进程不存在（无二维码）时发告警而非抛错 |
| AC5 | 通知渠道不可用时：记录失败、重试、不影响其它渠道 |
| AC6 | AstrBot 日志无 ERROR；单测通过；ruff 干净 |
| AC7 | WebUI 页面可查看状态并手动重发二维码 |
